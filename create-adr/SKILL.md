# Создание ADR

Создавай ADR как самостоятельный документ решения. Не реализуй описанное решение, не отправляй ветку и не запускай deployment без отдельного запроса.

## Подготовка

1. Прочитай инструкции репозитория и проверь `git status`, текущую ветку и существующие файлы `docs/adr`.
2. Сохрани принятый в репозитории формат. Если ADR ещё нет, используй формат ниже.
3. Для нового ADR возьми следующий свободный четырёхзначный номер. Имя файла: `NNNN-short-english-slug.md`.
4. Проверь фактический код, конфигурацию и документацию, на которые опирается решение. Отделяй существующее состояние от предлагаемого.

## Формат

Весь текст ADR, включая заголовки и пояснения, пиши на русском языке. Имена API, классов, команд, параметров и другие технические идентификаторы сохраняй без перевода.

```markdown
# ADR NNNN: Краткое название решения

- Статус: Предложено | Принято | Отклонено | Заменено ADR NNNN
- Дата: YYYY-MM-DD

## Контекст

Проблема, ограничения и подтверждённое текущее состояние.

## Решение

Выбранный подход и его существенные правила.

## Последствия

Положительные эффекты, компромиссы, риски и операционные обязанности.

## Альтернативы

Рассмотренные варианты и причины отказа. Раздел можно опустить, если альтернативы не обсуждались и их перечисление было бы выдумкой.

## Критерии приёмки

Проверяемые условия реализации. Раздел можно опустить для ADR без последующей реализации.
```

Не выдумывай факты, требования, альтернативы или согласование. Не включай секреты и чувствительные данные.

## Подтверждение владельца

Подтверждение не нужно, если пользователь прямо выбрал решение, одобрил уже показанный ADR или попросил лишь привести подтверждённое решение к формату.

Подтверждение нужно, если для ADR пришлось самостоятельно выбрать существенный вариант, который пользователь не утверждал, либо остались вопросы, меняющие архитектуру, security boundary, публичный контракт, хранение данных, стоимость или необратимость решения.

Если подтверждение нужно:

1. Создай или обнови файл со статусом `Предложено`.
2. Явно пометь внутри ADR нерешённые пункты и варианты без подмены их догадкой.
3. Не выполняй `git add` и не создавай коммит.
4. Покажи владельцу ссылку на файл и краткий список требуемых решений. Остановись и жди ответа.
5. После ответа сначала перечитай файл с диска: владелец мог изменить его вручную. Считай текущий файл источником истины, внеси только согласованные правки и поменяй статус на `Принято`, когда решение действительно подтверждено.

## Проверка и коммит

Перед коммитом:

- проверь структуру, русский язык и согласованность статуса;
- выполни `git diff --check`;
- убедись, что в diff нет секретов или реальных credential values;
- соблюди репозиторный Git workflow и работай в допустимой task-ветке;
- застейджи только созданные или изменённые ADR-файлы, не затрагивая чужие изменения.

Если подтверждение не требуется или уже получено, создай атомарный коммит в стиле репозитория. Commit message пиши на английском и с ticket prefix, например `KON-0000: Add: DARI credential import ADR.` Не push без отдельного запроса.
